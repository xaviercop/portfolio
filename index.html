Race Telemetry Pipeline

A containerised microservices pipeline that simulates trackside race telemetry and ingests it live.

Two services, two languages, talking over HTTP. A Python generator stands in for the car — emitting a continuous stream of tyre degradation, G-force and RPM readings — and a .NET ingestion API consumes it at speed. Nothing here is real race data; the point was to build the shape of the system a telemetry team actually runs, and to work in a stack I hadn't used before rather than reaching for the one I already know.

  • A data source that behaves like a sensor

    The Python service produces readings on a tick rather than in a batch, so the consumer has to cope with data arriving continuously and out of its control. Values move the way the underlying physics would — tyres degrade over a stint, they don't jump.

  • Ingestion that doesn't block

    The ASP.NET Core Web API takes the stream asynchronously using C# async/await, so requests queue and complete without a thread sitting idle waiting on I/O. This was the part that taught me most: the async model in C# is stricter than what I was used to in Python.

  • One container per service

    Each component got its own Dockerfile and its own isolated environment, then Docker Compose to wire them onto a shared network so the generator could reach the API by service name rather than by address. It runs the same on any machine that has Docker.

  • Then run it the way it would actually be run

    Deployed onto a local Kubernetes cluster with Minikube, with the deployments and services written as YAML manifests. Compose proves the containers talk to each other; Kubernetes is what the same setup looks like once something has to restart itself and stay reachable.

AgenticDesk

An AI receptionist that cosmetic and dental clinics embed on their own website.

Clinics drop a single script tag onto their site. A conversational agent then handles first contact with prospective patients — capturing their details and what treatment they're asking about — and turns each conversation into a qualified lead in a clinic dashboard, with an email to the front desk. I built and run the whole thing on my own: the React front end, the FastAPI back end, the database, auth, the embeddable widget, the test suite, deployment across three hosting providers, and the first round of outreach to clinics in Leicester and the Midlands.

The parts I'd point an engineer at aren't the features. They're the things that were quietly broken, and how they got found.

  • A safety net that had never fired

    While fixing an unrelated rate-limiter bug I noticed the daily AI spend cap was resetting at random. A date-string comparison meant the counter kept wiping itself, so the guard against a runaway API bill had never actually enforced anything in production.

  • A widget that failed dishonestly

    A copied embed key on an unauthorised site still rendered the clinic's full branding, then died mid-conversation with a generic connection error — it looked trustworthy right up until a real visitor hit it. I rebuilt config loading so an unauthorised embed renders nothing at all.

  • A security review nobody asked for

    A self-directed audit turned up an XSS hole on a test page and a rate-limiter bypass that chained across four separate layers. Both were fixed with regression tests. The fixed-window limiter was replaced with a sliding window, and JWT verification was hardened in two deliberate stages so a wrong issuer value couldn't lock out every user at once.

  • A compliance page I chose not to publish

    Auditing the data model rather than the policy text, I flagged that clinic treatment-interest data may count as special category health data under UK GDPR Article 9 — a higher bar than ordinary personal data. The privacy page is written but stays unrouted and marked draft until that question is answered properly. Shipping copy that reads compliant without being confirmed compliant seemed worse than shipping nothing.

Riaz & Sons Solutions

The first website for a Lahore engineering contractor trading since 1965.

Elevators, escalators, HVAC and industrial power generation — four service lines, sixty years of projects, and until this build, nothing online at all. The brief was less “make a website” than “work out what this company actually sells, then make it legible to someone who needs a lift installed.”

The interesting constraints were the ones the client couldn't see.

  • A site nobody would maintain

    An engineering firm with no in-house technical staff can't be handed a build pipeline. Vanilla HTML, CSS and JavaScript, no framework, no dependencies to go stale — the site renders from the files on the server and will still do so in five years, unattended.

  • An enquiry assistant with nothing behind it

    Visitors arrive knowing they need something and not what it's called. A client-side assistant classifies each message by intent — lifts, HVAC, power, pricing — and either answers from the service data or routes to a proposal request. It runs entirely in the browser, so there's no server to keep alive and no per-message cost for the client to cancel later.

  • Every path ends somewhere

    The failure mode for a contractor's site is a visitor who reads, nods and leaves. Proposal form, WhatsApp click-to-chat, direct call lines and a mapped office — four exits, sized to how ready the visitor actually is, rather than one contact page at the end.

  • Sixty years, ordered

    Most of the work was editorial: turning four overlapping service lines, three European partner distributions and decades of unlabelled project history into a hierarchy with deep links, so a procurement officer looking for escalator specifications lands on escalator specifications.

Mystery Infection

A diagnostic case study that asks the student to commit to an answer.

A 28-year-old man returns from Ghana. Ten days later: fever, chills, severe headache, muscle pain. The resource presents the history and symptoms, offers four plausible parasites, and makes the student choose before it reveals anything. Only then does it work through the transmission cycle, the incubation window that matches the timeline, and — the part that actually teaches — why each of the other three answers was wrong. It closes on three takeaways about travel history, incubation periods and endemic disease.
